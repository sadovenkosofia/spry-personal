# 0008. Which Google Cloud service for each piece of Spry

Status: proposed (draft: check every decision against what you actually want to defend)

## Context

Lab 9 asks what it would take to run Spry on another cloud. Spry on AWS today (see `infra/`
and ADR 0006, 0007): a static frontend on S3 + CloudFront, an API container, Aurora Serverless
v2 in private subnets (no NAT), Cognito with Google sign-in, a weekly report pipeline
(EventBridge Scheduler, SQS, builder Lambda, S3, mailer Lambda, SES) and an agenda parser
Lambda that calls Bedrock (Claude Haiku 4.5). The account has a $5 monthly budget alarm, so an
idle month should cost close to nothing.

The Google Cloud project is `avid-sphere-510417-m1`. The core (frontend, API, database) is
described in `gcp/*.tf` and validates, but it could not be deployed: the free-trial billing
account requires a prepayment, and the course does not require paying. Cloud Run, Cloud SQL,
Artifact Registry and Secret Manager all need a linked billing account, so replacing only the
database would not have helped. What is deployed instead is the one piece that works on the
Firebase Spark plan (no billing): the frontend on Firebase Hosting, calling the API and the
database that stay on AWS. See "What actually runs".

## Decision

| Spry on AWS | On Google Cloud | Decision | Why |
|---|---|---|---|
| S3 + CloudFront + WAF | Firebase Hosting | **replace** | CDN and certificate included, free plan, `/api/**` rewrite to Cloud Run gives one origin and no CORS. A bare Cloud Storage bucket would need a load balancer for HTTPS. |
| API container (ECS) | Cloud Run | **replace** | Same Docker image, scales to zero. Only change: the container listens on `$PORT`. |
| ECR | Artifact Registry | **replace** | 0.5 GB free, enough for one image. |
| Aurora Serverless v2 (pauses) | Cloud SQL for PostgreSQL, `db-f1-micro` | **replace**, see below | Same engine, so models, Alembic migrations and JSONB columns do not change. |
| Cognito + Google | Identity Platform | **keep Cognito** | Holds real accounts (ADR 0007: never replace the pool). Moving it means a user migration and rewriting `react-oidc-context` config. Stretch goal. |
| EventBridge Scheduler | Cloud Scheduler | **keep** | Works; the pipeline it triggers stays on AWS. |
| SQS | Pub/Sub or Cloud Tasks | **keep** | Part of the report pipeline, which stays together. |
| S3 reports + event to Lambda | Cloud Storage + Eventarc to Cloud Run | **keep** | Same reason. |
| SES | no Google service | **keep SES** | Multicloud is allowed. If moved: SendGrid or Mailgun, API key in Secret Manager. |
| Bedrock (Claude Haiku 4.5) | Vertex AI (Gemini, Claude via Model Garden) | **keep for now** | The parser works, is tested against Bedrock prices, and is outside the VPC on purpose (ADR 0006). Stretch: compare Gemini or Claude on Vertex AI. |
| Secrets (workspace variables) | Secret Manager | **replace** for the GCP side | `DATABASE_URL` and the DB password are generated by Terraform and stored there, never in Git. |
| CloudWatch Logs | Cloud Logging | **replace** | Automatic for Cloud Run. |
| IAM roles | Service accounts | **replace** | `spry-api` runs the API with only `cloudsql.client` and access to one secret. No downloaded keys. |
| Terraform `aws` provider, workspace `demo-dev` | Terraform `google` provider, workspace `spry-gcp` | **separate** | One plan must not be able to break both clouds. |

### The database

| Option | Latency | Monthly cost (idle) | Code |
|---|---|---|---|
| Cloud SQL, always on | same region as Cloud Run, a few ms | $9.37 ($7.67 compute + $1.70 storage) | unchanged |
| Cloud SQL, stopped when unused | same, but a stopped instance returns errors until started | $1.70 stopped, plus $0.0105 per running hour | unchanged, plus a stop/start habit (`make gcp-db-stop`) |
| Firestore | same region, no instance | $0 within the daily free quota | rewritten: no SQL, no joins, no CHECK constraints (`ends_at > starts_at` moves into code), no Alembic, JSONB becomes native maps |
| Keep Aurora, call it from Cloud Run | `eu-central-1` to `us-central1`, roughly 100+ ms per query, several queries per request | Aurora stays at ~$0.30, plus cross-cloud transfer | unchanged, but Aurora is in private subnets with no NAT: it would have to be made reachable from the internet |

**Chosen: Cloud SQL `db-f1-micro`, stopped when not in use.** It is the only option that keeps
the data layer unchanged and does not weaken Aurora's network isolation. Firestore is cheaper
but is a rewrite of the data layer to save about $9 a month. Calling Aurora across clouds adds
latency to every query and needs a public database endpoint.

### E-mail

SES stays. The mailer Lambda needs verified identities and IAM permissions that already exist,
and Google Cloud has no mail-sending service. If the report moved, the provider would be
SendGrid or Mailgun, and its API key would live in Secret Manager, read by the Cloud Run
service account, not in the repository or in an environment variable in Terraform.

### What would not move, and why

- **Cognito sign-in.** Real accounts; a migration is risky for no gain.
- **The weekly report pipeline.** It is a chain of AWS services (Scheduler, SQS, Lambda, S3,
  SES) and the builder reads Aurora from inside the VPC. Splitting it across clouds adds
  egress and cross-cloud credentials.
- **The agenda parser.** It calls Bedrock, runs outside the VPC by design (ADR 0006), and its
  cost was measured against Bedrock prices.

## Consequences

- The GCP database is a separate copy. The weekly report keeps reading Aurora, so the two
  databases diverge unless data is exported with `pg_dump`.
- The frontend on Firebase still signs in through Cognito and calls the AWS parser, so the
  Firebase URLs (`https://avid-sphere-510417-m1.web.app`) must be added to `callback_urls`,
  `logout_urls` and `allowed_origins` in `infra/terraform.tfvars`.
- The Cloud Run service is public (Firebase calls it without a Google identity) and the API
  does not check tokens yet, the same as on AWS.
- **Deployment of the full move is blocked by billing, not by design.** The Terraform in `gcp/`
  passes `terraform validate`, but `apply` was not run.

## What actually runs

| Piece | Planned (Part 2) | Actually deployed |
|---|---|---|
| Frontend | Firebase Hosting | Firebase Hosting (Spark plan, free) |
| API | Cloud Run | AWS ECS (unchanged), reached cross-origin through CloudFront |
| Database | Cloud SQL | Aurora (unchanged), "keep the database on AWS and call it across clouds" from the options above |

Cross-cloud costs of this split: the browser calls AWS directly, so every API call crosses the
Firebase and CloudFront origins (CORS preflight on POST and PUT), and the frontend needs
`VITE_API_BASE`. There is no database latency or egress between clouds, because the API and
Aurora stay together.
